# การใช้ระบบปฏิบัติการแบบเวลาจริง (RTOS)

## 1. ภาพรวม

Firmware ของอุปกรณ์ (DrowsyFW) ทำงานบน ESP32-S3 ซึ่งมี 2 core โดยใช้ **FreeRTOS** ที่มากับ ESP-IDF (Arduino core ของ ESP32 สร้างขึ้นบน ESP-IDF และ FreeRTOS อยู่แล้ว) ระบบไม่ได้ทำงานทั้งหมดใน `loop()` แต่แยกงานออกเป็น task อิสระหลายตัว แต่ละ task ถูกตรึงไว้กับ core ด้วย `xTaskCreatePinnedToCore` และกำหนด priority ตามความสำคัญของงาน

เหตุผลที่ต้องใช้ RTOS คือในระบบมีงานหลายประเภทที่มีจังหวะเวลาต่างกันมาก

- **การประมวลผลภาพ** ใช้เวลาราว 150–250 ms ต่อเฟรม และต้องทำต่อเนื่องตลอดเวลา
- **การเตือนด้วยเสียงและไฟ** ต้องตอบสนองเร็วและสม่ำเสมอ จังหวะเสียงต้องไม่ขึ้นกับความเร็วของการประมวลผลภาพ
- **งานเครือข่าย** ได้แก่ WiFi, เว็บเซิร์ฟเวอร์, TLS และการส่งข้อมูลขึ้น Cloud งานกลุ่มนี้อาจบล็อกนานหลายวินาทีโดยคาดเดาเวลาไม่ได้
- **การบันทึกไฟล์** ลง Flash (FFat) ทุก 1 วินาที

หากเขียนแบบ super loop งานเครือข่ายที่บล็อกจะทำให้การตรวจตาและการเตือนหยุดตามไปด้วย ซึ่งยอมรับไม่ได้ในระบบความปลอดภัย

## 2. การแบ่ง task และ core

แนวคิดหลักคือ **Core 1 ใช้สำหรับงานที่ต้องตรงเวลา และ Core 0 ใช้สำหรับงานเครือข่ายและงานเบื้องหลัง** งานที่บล็อกนานจึงไม่ไปแย่ง CPU ของงานตรวจจับและการเตือน

| Task | Core | Priority | Stack | รอบการทำงาน | หน้าที่ |
|---|---|---|---|---|---|
| `vision` | 1 | 5 | 16 KB | ต่อเนื่อง (รอเฟรมจากกล้อง) | ดึงภาพ → หาหน้า → หาตา → CNN → ตัดสินความง่วง |
| `alert` | 1 | 3 | 4 KB | 20 ms | ควบคุม buzzer, LED และอ่านปุ่มปิดเสียง |
| `sensor` | 1 | 2 | 3 KB | 500 ms | อ่าน LDR แล้วเปิด/ปิดไฟ IR |
| `net` | 0 | 2 | 6 KB | 1 s | เปิด AP, ต่อ WiFi, NTP, mDNS และเริ่มเว็บเซิร์ฟเวอร์ |
| `log` | 0 | 2 | 4 KB | 1 s + ทันทีเมื่อมี Event | บันทึก Sample และ Event ของ Trip ลง FFat |
| `sync` | 0 | 1 | 8 KB | 1 s | ส่ง Trip ขึ้น Supabase ผ่าน HTTPS |
| `oled` | 0 | 1 | 4 KB | 200 ms | วาดหน้าจอ OLED ผ่าน I²C |
| `loop()` (loopTask ของ Arduino) | 1 | 1 | ค่าเริ่มต้น | 50 ms | พิมพ์สถานะทุก 5 วินาที และสั่งรีบูตหลัง OTA |

นอกจาก task ในตาราง ยังมี task ที่ไลบรารีสร้างเอง ได้แก่ task ของ AsyncTCP ซึ่งรันเว็บเซิร์ฟเวอร์ (ESPAsyncWebServer) และ task ของ WiFi/LwIP

**เหตุผลของการตั้ง priority**

- `vision` ได้ priority สูงสุด เพราะเป็นงานหลักของระบบ และส่วนใหญ่ของเวลา task นี้รอเฟรมจาก driver กล้องอยู่ ระหว่างนั้น task อื่นบน Core 1 จึงได้ CPU
- `alert` มี priority ต่ำกว่า `vision` แต่ตื่นทุก 20 ms เมื่อตื่นขึ้นมา scheduler จะสลับไปทำ `alert` ก่อน `vision` เสมอถ้า `vision` กำลังรอหรือถูก block ทำให้จังหวะเสียงเตือน (เช่น ดัง 200 ms ทุก 600 ms ที่ระดับ 2) คงที่แม้อัตราเฟรมจะตกไปเหลือ 3 fps
- `sync` และ `oled` ได้ priority ต่ำสุด เพราะเลื่อนเวลาได้โดยไม่กระทบความปลอดภัย

## 3. การสื่อสารและการป้องกันข้อมูลระหว่าง task

### 3.1 SharedState + Mutex

สถานะทั้งระบบ (Eye State, ระดับความง่วง, PERCLOS, fps, สถานะ WiFi, ค่า LDR ฯลฯ) อยู่ใน struct `SharedState` ตัวเดียว ป้องกันด้วย mutex (`xSemaphoreCreateMutex`)

- **ฝั่งเขียน** ใช้ `StateGuard` ซึ่งเป็น RAII guard ที่ lock ใน constructor และ unlock ใน destructor จึงไม่มีทางลืม unlock
  ```cpp
  { StateGuard g; g_state.ldrRaw = raw; g_state.irOn = irOn; }
  ```
- **ฝั่งอ่าน** ใช้ `stateSnapshot()` ซึ่งคัดลอก struct ทั้งก้อนออกมาภายใต้ lock แล้วค่อยนำไปใช้นอก lock ทำให้ถือ mutex สั้นที่สุด และค่าทุกช่องที่อ่านได้มาจากช่วงเวลาเดียวกัน (consistent snapshot)

FreeRTOS mutex มี priority inheritance ในตัว จึงลดปัญหา priority inversion เมื่อ task priority ต่ำ (เช่น `oled`) ถือ lock อยู่ขณะที่ `vision` ต้องการ lock

### 3.2 Queue สำหรับ Event

เมื่อ `DrowsinessJudge` ตรวจพบเหตุการณ์ (เปลี่ยนระดับ, Microsleep, Distraction) task `vision` จะส่ง Event เข้า queue ขนาด 32 ช่อง (`xQueueCreate(32, sizeof(DrowsyEvent))`) ด้วย timeout 0 จึงไม่รอแม้ queue จะเต็ม จากนั้น task `log` บน Core 0 รับ Event ไปพิมพ์ Serial และเขียนลงไฟล์

task `log` ใช้ `xQueueReceive` โดยตั้ง timeout เท่ากับเวลาที่เหลือก่อนถึงรอบบันทึก Sample ถัดไป การเรียกครั้งเดียวจึงทำได้สองหน้าที่ คือรอ Event และทำหน้าที่เป็นตัวจับเวลา 1 วินาที

**เหตุผลที่ต้องแยก:** ในเวอร์ชัน 0.2.6 พบว่าถ้า `vision` พิมพ์ Serial เอง ขณะที่ไม่มีโปรแกรมใดเปิดพอร์ต USB CDC อยู่ การเขียนจะค้างได้ราว 3 วินาที การตรวจตาจึงหยุดไปด้วย หลังย้ายงาน I/O ทั้งหมดไปไว้ที่ task อื่นผ่าน queue ปัญหานี้หายไป

### 3.3 Try-lock เพื่อไม่ให้งานหลักถูกบล็อก

ภาพสด (`/snapshot.jpg`) และภาพตา (`/eyes.raw`) ที่หน้าเว็บขอ ใช้ buffer แยกพร้อม mutex ของตัวเอง

- `vision` (ผู้ผลิต) เรียก `xSemaphoreTake(mutex, 0)` ถ้าเว็บกำลังอ่านอยู่จะ **ข้ามเฟรมนั้นไปทันทีโดยไม่รอ**
- เว็บ (ผู้ใช้ข้อมูล) รอได้สูงสุด 200–500 ms

ด้วยวิธีนี้ งานตรวจจับจะไม่ถูกหน่วงจากจำนวนคนที่เปิดหน้าเว็บ

**ปัญหาที่พบและวิธีแก้:** เดิมฝั่งเว็บถือ mutex ไว้ตลอดช่วงวาดกรอบและเข้ารหัส JPEG (~150–200 ms) ทำให้ `vision` ข้ามการเก็บภาพแทบทุกเฟรม และหน้าเว็บได้ภาพเดิมซ้ำ (ภาพค้าง) จึงแก้ให้ถือ mutex เฉพาะตอนคัดลอก buffer แล้วปล่อย lock ก่อนเข้ารหัส

### 3.4 Recursive Mutex สำหรับระบบไฟล์

ไฟล์ Trip บน FFat ถูกใช้จากสาม task คือ `log` (เขียน), `sync` (อ่านเพื่อส่ง Cloud) และเว็บ (อ่านเพื่อแสดงประวัติ) ฟังก์ชันจัดการไฟล์บางตัวเรียกซ้อนกัน จึงใช้ `xSemaphoreCreateRecursiveMutex` ห่อด้วย RAII guard `FsGuard` เพื่อไม่ให้ task เดียวกัน deadlock ตัวเอง

### 3.5 กฎ: ห้ามส่ง camera frame buffer ข้าม core

frame buffer ของกล้อง (`camera_fb_t`) ต้องคืน driver ภายใน task `vision` เท่านั้น ถ้าต้องการภาพข้าม task ให้คัดลอกเข้า buffer แยกตามข้อ 3.3 เพื่อไม่ให้ driver ขาด buffer และเพื่อให้ ownership ของหน่วยความจำชัดเจน

## 4. การจัดการหน่วยความจำร่วมกับ RTOS

- stack ของแต่ละ task กำหนดตามงาน `vision` ได้มากที่สุด (16 KB) เพราะเรียก ESP-DL และ TFLite Micro ส่วน `sync` ได้ 8 KB เพราะใช้ TLS
- RAM ภายในหลังเปิด WiFi และโหลด ESP-DL เหลือก้อนใหญ่สุดราว 30 KB buffer ใหญ่ทั้งหมด (buffer ส่ง Cloud, ภาพตาดิบ, buffer ของ mbedTLS) จึงจองจาก PSRAM ด้วย `heap_caps_malloc(..., MALLOC_CAP_SPIRAM)` และ `mbedtls_platform_set_calloc_free`

## 5. ผลที่ได้

- การตรวจตาและการเตือนทำงานต่อได้ขณะต่อ WiFi ไม่ติด, ขณะส่งข้อมูลขึ้น Cloud และขณะมีคนเปิดหน้าเว็บ
- จังหวะเสียงเตือนคงที่ เพราะ `alert` เป็น task แยกที่ตื่นทุก 20 ms และไม่ขึ้นกับอัตราเฟรม
- logic ความง่วงนับเวลาจริง (ผลต่างของ `millis()`) ไม่นับจำนวนเฟรม ผลจึงถูกต้องแม้ fps จะแกว่งตามโหลดของระบบ (วัดได้ 2–7 fps)

## 6. ข้อจำกัด

- รอบเวลาของทุก task ใช้ `vTaskDelay` ซึ่งเป็น delay แบบสัมพัทธ์ ไม่ได้ใช้ `vTaskDelayUntil` รอบจึงคลาดได้เท่ากับเวลาที่ใช้ทำงานในแต่ละรอบ (task `log` ชดเชยเองด้วยการคำนวณเวลาครั้งถัดไป)
- ยังไม่ได้วัด stack ที่ใช้จริงของแต่ละ task (`uxTaskGetStackHighWaterMark`) ขนาด stack ปัจจุบันจึงตั้งจากการลองแล้วไม่ล้ม
- ยังไม่ได้ใช้เครื่องมือวัดเวลา CPU ของแต่ละ task จึงยังไม่ทราบสาเหตุที่อัตราเฟรมบางช่วงตกเหลือ 2–3 fps แม้ไม่มีโหลดจากเว็บหรือการส่ง Cloud
